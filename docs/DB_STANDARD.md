# ASLMS Database Standard (v1.2, 30 Sep 2026 — approved for execution)

Binding standard for every table, column, key and identifier in ASLMS v2 (`backend/`). It is written against
the database that exists today: migrations `0001_phase1_core`, `0002_ownership_unit`, `0003_phase2_workflow`,
49 application tables in `public`, documented in `docs/schema/phase1.md`. Where this document and
`docs/schema/phase1.md` disagree, this document wins and the schema document is updated in the same commit.
Where this document and the Plan (`docs/Legal_Case_Monitoring_Portal_Plan.docx`) disagree, the Plan wins and
the conflict is logged in `docs/claude_ASLMS_design_decisions.md` before anything is built.

Version history: v1.0/v1.1 (29 Sep) were drafted against the September prototype's 56-table schema and are
superseded; v1.2 maps the same decisions onto the real inventory.

Sources: PostgreSQL community conventions; RFC 9562 (UUID v7); RFC 3339 / ISO 8601; MeitY *Metadata and
Data Standards* (MDDS); Local Government Directory (LGD) codes; the eCourts CNR; eOffice file numbering as
used in the Assam Secretariat.

---

## 0. Table classes

Every table is one of four classes. The class is declared in the table's `COMMENT ON TABLE` as
`class=<reference|master|transaction|derived>` and as `__table_class__` on the model. It fixes who may write
the table and how it is filled. This is the master-table / transaction-table separation used across NIC and
State systems, under PostgreSQL naming (plain plural nouns; `ref_` prefix for code sets; no `_master` suffix —
decision closed with the owner, 29 Sep).

| Class | Tables today | Written by |
|---|---|---|
| **Reference** (`ref_*`) | new in this milestone (§7) | `aslms seed` (upsert on `code`); administrators edit labels only |
| **Master** | `offices`, `users`, `courts`, `benches`, `case_types`, `counsel_codes`, `office_name_patterns`, `office_keywords`, `office_watchlist`, `user_notification_preferences`; new: `designations`, `states`, `districts`, `acts`, `advocates` | administration screens (organisation masters) or the `master_sync` job (court masters) |
| **Transaction** | `cases`, `case_parties`, `case_advocates`, `case_hearings`, `case_acts`, `case_links`, `causelists`, `causelist_entries`, `causelist_reconciliations`, `recommendations`, `case_ownership`, `ownership_transfers`, `documents`, `document_text`, `orders`, `next_dates`, `alerts`, `requests`, `request_messages`, `case_stages`, `case_notes`, `case_note_attachments`, `custody`, `assistant_conversations`, `assistant_messages`; new: `case_applications`, `case_lower_courts`, `case_objections` | users, the daily cycle, the scoring engine |
| **Derived / log** | `events`, `audit_log`, `custody_history`, `case_snapshots`, `case_office_scores`, `notifications`, `digests`, `otp_codes`, `refresh_tokens`, `job_runs`, `napix_call_log`, `source_failures`, `master_sync_runs`, `sourcetrace_ingestions` | system only; logs are INSERT-only, derived rows are regenerable |

Rules that follow from the class:
1. A transaction never stores a master value as free text once a master exists (`users.designation` →
   `designation_id`; `case_acts.act_name` → `act_id` with `act_name_as_listed` kept; `case_advocates.name` →
   `advocate_id` nullable with `name_as_listed` kept).
2. Court masters are synced, never typed (`master_sync`), keyed by the court's own code, never deleted on
   sync; rows absent upstream get `is_active=false`, `deactivated_at`.
3. Organisation masters are versioned: `offices` and `designations` gain `valid_from` / `valid_to`.
4. Masters are deactivated, never deleted. The four `DELETE` endpoints in `api/routers/admin.py`
   (codes, patterns, keywords, watchlist) become deactivation.
5. Master rows carry their external identifier as a UNIQUE column: `lgd_code` on `states`/`districts`,
   `case_type_code` / `bench_id` / `est_code` on court masters, Secretariat `code` on `offices`.

## 1. Naming

Already followed by the current schema and kept: lower snake_case; plural table names; `id` primary key;
`<entity>_id` foreign keys with a role prefix when an entity is referenced twice (`from_office_id`,
`to_office_id`); `is_`/`has_` booleans; `_at` instants; `_date` for court dates; `_by` actors; constraint
names only from `NAMING_CONVENTION` in `db/base.py`. Additions: `ref_` prefix for code-set tables;
Postgres enum types stay named as today.

## 2. Primary keys

```
id uuid PRIMARY KEY DEFAULT uuid_generate_v7()
```
UUID v7 (RFC 9562), time-ordered. Generated by the SQL function `uuid_generate_v7()` (Appendix A) as the
server default — replacing `gen_random_uuid()` in `db/base.py::uuid_pk()` — and by `uuid6.uuid7()` when the
application needs the id before flush. Business identifiers (CNR, `est_code`, `code`, email) are UNIQUE
columns, never keys. `custody.case_id` and `document_text.document_id` stay as 1:1 primary keys (they are
the parent's id, not a new identity). Lookup tables use `code` as their key (§7).

## 3. Reference numbers (`ref_no`)

Records people quote carry `ref_no varchar(40) NOT NULL UNIQUE` in the Secretariat's pattern:

```
ASLMS/<OFFICE>/<TYPE>/<YYYY>/<NNNNNN>      e.g. ASLMS/GOA/CASE/2026/001842, ASLMS/EDU/REQ/2026/000042
```
`OFFICE` = `offices.code` of the allocating office, or `GOA` when the system creates the record before any
department owns it. `TYPE` from `ref_record_type`. Sequence per (office, type, year) in `ref_sequences`
(Appendix C). Allocated once at insert; never changed on claim, transfer or merge. Accepted by the API
wherever an `id` is (`services/cases.py::resolve_case_ref` accepts `id`, `ref_no` or CNR).

| TYPE | table | allocating office |
|---|---|---|
| `CASE` | cases | `GOA` (daily cycle, search, link); the claiming office when created by discovery |
| `REQ` | requests | `from_office_id` |
| `NOTE` | case_notes | author's office |
| `DOC` | documents where `doc_group in (court_filing, internal)` | uploader's office |
| `TRF` | ownership_transfers | `from_office_id` |
| `NXT` | next_dates where `source = manual` | reviewer's office |
| `ALR` | alerts | `GOA` |

Court identifiers (CNR, `case_no_text`, `order_no`, `napix_causelist_id`) are stored exactly as issued.

## 4. Timestamps

Unchanged from today: `timestamptz` in UTC, IST in the API; court dates as `date`; `created_at` everywhere,
`updated_at` on mutable tables. Addition: `updated_at` maintained by a `set_updated_at()` trigger
(Appendix B) on every mutable table, so direct SQL is covered.

## 5. Audit columns

The existing `ActorSnapshotMixin` (`actor_user_id`, `actor_name`, `actor_designation`, `actor_office_code`)
is the standard and stays. Additions: `created_by` / `updated_by` (FK `users.id`, `ON DELETE SET NULL`,
NULL for system writes) on every master and transaction table users can write that does not already carry an
actor snapshot. `audit_log` unchanged.

## 6. Deletion and retention

Rows of legal significance are never deleted: cases and all `case_*`, causelists and entries,
recommendations, ownership, transfers, documents, orders, next_dates, alerts, requests, stages, notes,
custody, events, audit.

* Every FK to those tables is `ON DELETE RESTRICT`. Today 41 FKs cascade (20 to `cases`, 7 to `users`,
  5 to `offices`, 2 each to `documents`, `courts`, `causelists`, 1 each to `requests`, `case_notes`,
  `assistant_conversations`, `alerts`). After this milestone CASCADE remains only on: `otp_codes`,
  `refresh_tokens`, `user_notification_preferences` (→ users), `notifications`, `digests` (→ alerts/users),
  `case_office_scores` (→ cases; recomputed), `causelist_reconciliations` (→ causelists), `document_text`
  (→ documents), `sourcetrace_ingestions` (→ documents), `assistant_messages` (→ conversations),
  `napix_call_log` (→ job_runs). `uuid_fk()` default changes from `CASCADE` to `RESTRICT`.
* Lifecycle is state, not deletion: `case_ownership.status`, `recommendations.status`, `requests.status`
  already do this; add `archived_at` to `documents`, `closed_at` to `cases` (set on disposal + owner
  closure), `withdrawn_at` where a user can retract.
* `services/cases.py` line ~411 (`session.query(CaseParty)…delete()`) becomes an upsert on
  `(case_id, role, party_no)`; rows absent from the new dossier get `is_current=false`.
* Retention beyond the operational window (proposal: 10 years after closure; policy owner to confirm) is a
  move to `archive.*`, never DELETE. `napix_call_log` pruning (already planned) is the one exception and is
  a log, not a record.

## 7. Code sets: what becomes a lookup table

The schema uses 55 Postgres enum types. They stay for machine states. Eight sets that users see as labels,
filter on, or that an administrator may need to extend without a release become `ref_*` tables:

| today (enum) | becomes | why |
|---|---|---|
| `user_role` | `ref_role` | labels on screens, per-role descriptions |
| `office_kind` | `ref_office_kind` | Secretariat may add kinds (board, corporation) |
| `case_stage` (17 values) | `ref_case_stage` (+ `sort_order`, `phase`) | departments see the lifecycle as an ordered list |
| `request_kind` | `ref_request_kind` | extensible |
| `note_kind` | `ref_note_kind` | extensible |
| `doc_type` (13 values) | `ref_doc_type` (+ `doc_group`) | the filing vocabulary grows |
| `alert_kind` | `ref_alert_kind` (+ default severity, label) | admin-tunable |
| `event_type` | `ref_event_type` (+ timeline label, icon key) | timeline labels live in data, not code |

plus `ref_record_type` (§3). Shape:
```
ref_<set> (code varchar(40) PK, label varchar(120) NOT NULL, description text, sort_order int NOT NULL DEFAULT 0,
           is_active bool NOT NULL DEFAULT true, created_at, updated_at)
```
Business columns become `varchar(40) NOT NULL REFERENCES ref_<set>(code)`. The Python enums are kept as
constants (their values are the codes) so type hints and tests are unchanged; `seed` upserts one row per
member. The remaining 47 enum types (statuses, sources, channels, scan states…) stay native.

A reference-data migration writes its audit rows and events through `aslms/db/migration_audit.py`, so that a
re-application after a downgrade is recorded once and raises its events again.

## 8. Roles and grants

| Role | Use | Rights |
|---|---|---|
| `aslms_owner` | migrations | all |
| `aslms_app` | API, workers | SELECT/INSERT/UPDATE on master and transaction tables; INSERT only on logs; DELETE only on the §6 cascade list; no DDL |
| `aslms_readonly` | Grafana, reports, State-tier dashboards | SELECT |

The existing `aslms_forbid_change()` append-only triggers stay. `docker-compose*.yml`, `infra/` and
`.env.example` gain `DATABASE_URL` for `aslms_app` and `ASLMS_MIGRATE_URL` for the owner.

## 9. Schemas — deferred (revised recommendation)

v1.1 proposed PostgreSQL schemas per bounded context. With a live Next.js portal, Grafana dashboards,
pgbouncer and 70 tests all addressing `public`, the move costs more than it returns now. Decision: stay in
`public`, carry the class in `COMMENT ON TABLE` (§0), and revisit schemas when the District Court (Phase 3)
tables land. Only `archive` is created, on first use.

## Appendix A — `uuid_generate_v7()` (PostgreSQL 16)

```sql
CREATE OR REPLACE FUNCTION uuid_generate_v7() RETURNS uuid
LANGUAGE sql VOLATILE PARALLEL SAFE AS $$
  SELECT encode(
    set_bit(set_bit(
      overlay(uuid_send(gen_random_uuid())
              placing substring(int8send((extract(epoch from clock_timestamp())*1000)::bigint) from 3)
              from 1 for 6),
      52, 1), 53, 1), 'hex')::uuid;
$$;
```
PostgreSQL 18: replace the body with native `uuidv7()`.

## Appendix B — `set_updated_at()`

```sql
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END $$;
CREATE TRIGGER <table>_updated_at BEFORE UPDATE ON <table> FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

## Appendix C — reference-number allocation

```sql
CREATE TABLE ref_sequences (
  office_code varchar(20) NOT NULL,
  record_type varchar(10) NOT NULL REFERENCES ref_record_type(code),
  year        smallint    NOT NULL,
  last_value  integer     NOT NULL DEFAULT 0,
  PRIMARY KEY (office_code, record_type, year)
);
```
```python
def allocate_ref_no(session: Session, office_code: str, record_type: str, when: datetime | None = None) -> str:
    year = (when or now_ist()).year
    n = session.execute(text("""
        INSERT INTO ref_sequences (office_code, record_type, year, last_value) VALUES (:o, :t, :y, 1)
        ON CONFLICT (office_code, record_type, year)
        DO UPDATE SET last_value = ref_sequences.last_value + 1
        RETURNING last_value"""), {"o": office_code, "t": record_type, "y": year}).scalar_one()
    return f"ASLMS/{office_code}/{record_type}/{year}/{n:06d}"
```
The `INSERT … ON CONFLICT … RETURNING` form locks one sequence row, so concurrent allocations serialise
there and never on the business table. Gaps are allowed (a rolled-back transaction consumes a number);
duplicates are not.
